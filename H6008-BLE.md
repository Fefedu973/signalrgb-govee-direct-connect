# Optional H6008 BLE realtime transport

The `H6008Realtime` setting is disabled by default. It applies only to identified **H6008** devices configured with the existing **Solid color / protocol3** setting. It preserves the current controller ID, device ID, LAN address recovery and Canvas LED mapping.

This addon is the SignalRGB client. It requires a separately installed and configured BLE companion listening on **UDP127.0.0.1:47684**, with the intended bulbs allowlisted. No communication key, real bulb address, account information or BLE implementation is included in the addon. The companion performs authenticated BLE communication; the addon sends only stable device IDs, RGB values and control messages over loopback.

The backend's protocol was investigated on H6008 hardware1.07.03 / firmware1.01.25. This is not a compatibility claim for every H6008 revision. The BLE mode differs from ordinary LAN `colorwc`; no undocumented LAN transition parameter is added.

Enable the setting from the actual device page in SignalRGB. Version2.2.2 keeps that choice strict: if the companion stops responding, color updates pause and the last bulb color is held. It does not silently resume LAN `colorwc`, which would reintroduce fading. Disable the option explicitly to return to LAN colors.

## Transport and timing

The addon reuses each device's existing bound UDP socket and reply port. It does not bind another global socket or compete with discovery on port4002.

The BLE client is constructed only in the device renderer. Discovery controller data remains JSON-serializable for SignalRGB's JavaScript-engine boundary. Version2.2.1 corrects a circular owner reference introduced in2.2.0 and logs the effective H6008 opt-in, value type and eligibility once at initialization.

```json
{"id":1,"op":"colors","colors":[{"device":"00:00:00:00:00:00:00:01","rgb":[12,34,56],"on":true}]}
{"id":2,"op":"heartbeat","devices":["00:00:00:00:00:00:00:01"]}
{"id":3,"op":"release","devices":["00:00:00:00:00:00:00:01"],"restore":false}
```

The ID above is synthetic. Replies must come from loopback, match an outstanding request ID, and contain this device's stable ID. When SignalRGB exposes the sender port, it must also match47684. A usable reply has `ok` and `devices:[{device,state,ready,error,...}]`.

- Before the first acquisition, the addon obtains a current LAN status. If the bulb is off, it sends the existing LAN power-on command once and waits for an on-state confirmation. This preflight is bounded to two seconds; a missing status holds color updates and starts the cooldown. Once BLE has taken over, this power-on preflight never repeats, so a later user-initiated off state is respected.
- The first color after that preflight starts acquisition. LAN rendering and LAN power/mode commands are suppressed during BLE acquisition, streaming and release.
- Changed RGB values are sent at most every100ms. The latest Canvas or Forced color is sampled at each eligible frame; old frames are not queued.
- A heartbeat renews the companion's two-second lease every500ms, including when the RGB value is unchanged.
- Replies reporting `connecting`, `initializing` or `reconnecting` allow a bounded15-second acquisition window. Two seconds without a valid acknowledgement initiates release.
- `paused_off` keeps the lease without invoking the LAN renderer's automatic turn-on. The companion can resume when the bulb is turned on separately.
- An explicit failure or timeout sends `release` with `restore:false`. The addon waits for the release acknowledgement, or at most another two seconds for lease expiry, before entering the cooldown. Color updates remain paused throughout; no automatic LAN color fallback occurs while the option is enabled. A missing local socket, invalid RGB frame or UDP write exception also holds color updates.
- Failed acquisition is retried only after a30-second cooldown. Each acquisition remains bounded by the same reply and progress deadlines. Turning off the option releases BLE before returning to LAN. Explicit LAN power/status commands and the shutdown choices remain available.

The device page displays the transport phase and counters for local color requests, ready replies, failures and retries. These are not hardware or optical FPS measurements. An outage creates one visible alert; it clears after recovery or explicit opt-out. Status messages update at most once per second except on phase changes; phase changes and failures also go to the plugin log. This uses SignalRGB's documented [device alerts and messages](https://docs.signalrgb.com/developer/plugins/utilities/).

The companion must cancel pending connect/query/initialization work on release or lease expiry and prevent late realtime writes. A release acknowledgement must follow serialized cleanup. These requirements prevent competing BLE and LAN color streams; they are part of the backend contract, not functionality this JavaScript client can enforce inside a different process.

## Shutdown

| SignalRGB choice | Bridge request | LAN behavior |
|---|---|---|
| Release control | `release`, `restore:true` | No color or mode command from the addon. The companion restores the initial color mode. |
| Single color | `release`, `restore:false`, `final_rgb:[r,g,b]` | Final color is delegated to the companion after stopping its stream; no competing LAN color command. |
| Turn device off | `release`, `restore:false` | Existing LAN turn-off commands follow; the companion must never restore power or brightness. |

Shutdown can replace an already pending outage release with its restore/final-color policy. Only the acknowledgement of the newest release can complete that transition. The companion must also serialize consecutive releases and retain the latest policy. If there is no active BLE lease, including during the cooldown, the original explicit LAN shutdown behavior applies; an intentional Single color shutdown is therefore still permitted.

SignalRGB can destroy the device socket immediately after `Shutdown`. Finalization is therefore performed by the companion; the addon cannot promise to receive the final acknowledgement during process shutdown. The backend must implement `final_rgb` for Single color, and report a final-color failure if its bounded reconnect/authentication attempt fails. Abrupt process termination relies on lease expiry.

## Validation

Run `node tests/ip-recovery.cjs` and `node tests/ble-bridge.cjs`. Tests execute the production classes with synthetic IDs, documentation-only IP addresses, fake time and substituted host I/O. They cover unchanged LAN packets for other device/protocol combinations; initial off-state power-on and missing-status hold; acquisition; reply filtering; cadence; heartbeat; timeout; bounded reconnection; release and cooldown; repeated outages without LAN colors in Canvas and Forced modes; missing sockets; UDP write errors; alert clearing; status throttling; explicit opt-out; later off-state handling; all three shutdown choices; and shutdown policy promotion during a pending release.

These tests do not contact lights and do not establish optical latency, simultaneous three-bulb performance or reliability on an untested firmware. Hardware integration needs separate validation with the actual companion and bulbs.
